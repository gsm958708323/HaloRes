# UI 运行时代码分层

状态：已采纳，2026-11-04。

## 背景

UI 迁移和导航记录已确定运行时行为，但将门面、配置、导航状态、实例所有权、视图生命周期、
Unity 表现和调度逻辑放在同一目录，阅读时需要在行为和实现细节之间来回跳转。目标是改善定位
与职责辨识，同时保留当前可验证的运行方式，不引入尚无需求支撑的运行时扩展点。

## 决策

保留一个 `GameFramework.UI` Unity Assembly，在现有运行时目录内按职责组织文件：

| 目录 | 职责 |
| --- | --- |
| `API` | 对外 `UIManager` 门面与一次访问对应的 `UIHandle` |
| `Configuration` | 序列化配置、启动校验与只读运行时定义 |
| `Navigation` | 纯 C# 访问记录、顺序、快照和可见性派生规则 |
| `Instances` | 根视图实例唯一性、引用计数及 AssetScope 所有权 |
| `Views` | 视图生命周期、父子视图选择与 Item 管理 |
| `Unity` | 根节点、Canvas 层和渲染开关 |
| `Runtime` | 串行化导航命令，并协调 AssetSystem、实例、生命周期和 Unity 表现 |

`UIManager` 只转发稳定的业务 API。`UINavigationModel` 不调用 Unity API，也不加载资源；
`UIViewInstanceStore` 通过项目现有 `AssetSystem` 创建和释放作用域。`UIRuntime` 是运行时
协调入口，承接跨职责的流程，但不新增事件总线、服务定位器、接口工厂或资源桥接脚本。

这些目录表达当前职责边界，不单独拆成多个程序集。现有类型仍属于同一 Unity Assembly，
因此目录本身不构成编译期依赖约束；只有出现独立编译、独立复用或明确的循环依赖治理需求时，
才评估拆分程序集，并先确认 Unity asmdef 与测试依赖能够形成无环引用。

## 结果

导航规则可通过纯 C# EditMode 测试验证，资源生命周期仍由 `AssetScope` 管理，视图生命周期
名称和调用约定保持原样。目录可让维护者按 API、规则、所有权、Unity 适配和调度分别定位代码。
代价是 `UIRuntime` 仍承担跨层编排，且同程序集的目录边界依赖代码约定；若未来协调流程继续增长，
应先基于实际变化拆分职责，再考虑新的抽象或程序集。

## 验证

目录分层不改变 UI 生命周期命名、导航契约或 AssetSystem 资源加载入口。重构验证状态见
`Docs/verification/2026-11-04-ui-layering.md`；2026-11-02 的 94 项测试记录属于分层调整前的基线。
